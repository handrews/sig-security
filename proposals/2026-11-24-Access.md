## Introduction

Both OAuth 2 and GNAP feature a relatively complex structure for requesting
access to a resource.  Both features have RAR as their acronym, and share
the same general JSON structure as they were developed together.

GNAP RAR stands for _Resource Access Rights_ and is part of the core GNAP
specification as
[Section 8 of RFC9635](https://www.rfc-editor.org/info/rfc9635/#section-8).
It allows specifying information either in the JSON structure or as
a pre-defined string known to the Authorization Server (AS);
this option is somewhat equivalent to OAuth 2 scopes.

OAuth 2 RAR is
[RFC9396 Rich Authorization Requests](https://www.rfc-editor.org/info/rfc9396/).
It only supports the JSON structure as it can be used alongside scopes,
and since it was a later addition, support for it is advertised via
OAuth2 metadata ([RFC8414](https://www.rfc-editor.org/info/rfc8414)).

## Motivation

OAuth 2 RAR has become recommended or mandatory in many high-security
industries.  GNAP is an emerging standard with institutional backing.

## Proposed solution

The proposed solution is an enhancement of the existing
Security Requirement Object system to describe the necessary RAR structures
in the Security Requirement Object in place of scopes.

Note that the "Minimal GNAP Support" proposal already extends this system
by allowing GNAP access reference strings in place of scopes, as they are
roughly analogous to OAuth 2 scopes and are likewise simple strings.
As these strings are also allowed to be used with other Security Scheme
types in a rather vague and under-specified way, the use of reference
access strings fit within the existing design.

Adding RAR support is a larger enhancement that requires allowing each
array entry to be either a string (as it is now) or a JSON object.

### Terminology

As the two RARs stand for completely different sets of words, it is
necessary to pick a word to use with this feature as "RAR" is a bit
too generic.

The term ***Access*** is used in this proposal for field and Object
names.  The other option is "Authorization", which is already somewhat
overloaded.

### Per-operation vs per-call information vs "location"

RAR structures have a few basic types of information:

* The `type` field, which determines the rest of the structure
* The `location` field, which can be used to constrain the set of servers
  (and possibly paths?  I'm unclear) where the authorization is valid
* Operation-specific fields, such as whether you need read or write access
* Request-specific fields, such as the amount of money involved in a
  transaction

The `type` field and the operation-specific fields are known at design
time, and can therefore be hardcoded into the OpenAPI Description.

The `location` field may be hard-codable, or may be derivable from the
operation or endpoint, or might align with the choice of server from
the list of Server Objects.

Request-specific fields are essentially additional operation parameters,
and may in fact correlate with query parameters, body fields, or other
data.

Let's look at an example, adapted from the OAuth 2 RAR RFC:

```yaml
type: payment_initiation
actions:
- initiate
- status
- cancel
locations:
- https://example.com/payments
instructedAmount:
    currency: EUR
    amount: "123.50"
creditorName: Merchant A
creditorAccount: {
    bic: ABCIDEFFXXX
    iban: DE02100100109307118603
remittanceInformationUnstructured: Ref Number Merchant
```

In this example, `type` and `actions` are operation-specific, although
in theory `actions` could be request-specific.  This appears to be
unusual but worth keeping in mind.

Part of the benefit of RAR is the ability to make authorization decisions
at the request granularity.  Caller A may only be authorized to transfer
up to 100 USD, while caller B may have unlimited transfer privileges.

For per-operation Security Requirement Objects, the operation-specific
fields are best provided as plain data, as inferring such things out
of a JSON Schema is not trivial, even when `const` is used.  Locating
which fields have a `const` value can be challenging when references
are involved, and schemas not easy for humans to read.

This proposal suggests providing as much of a literal data structure
as possible,

## Detailed Design

The Security Requirement Object is a JSON/YAML object where the property
names identify Security Schemes, and the property values currently require
an array that contains OAuth 2 scopes (which are declared in the OAuth
Flow Object).  This array can also contain strings used by other types
of Security Schemes, although the OAS provides no guidance on how to
use them, and no place in the Security Scheme to declare them.

* Allow the Security Requirement Object property value to be either
  an array (exactly as it is now) or a new type of Object called
  an Access Object
* The Access Object can allow various access request mechanisms,
  including OAuth 2 scopes, RAR access structures, and potentially
  a more formalized approach for other Security Schemes.

This proposal adds new features without disturbing existing usage.
